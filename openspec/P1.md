# UNIT: P1 — public landing data

REPO: barberbase-core
BRANCH: from clean main after O4, clean working tree

## Context

The customer flow's landing page (frontend unit U1) chooses booking mode
before services are known, and the services screen (U2) renders audience
chips from the location's own categories. Neither datum is on the public
location response today, so U1 and U2 cannot start.

This is the first PUBLIC unit in the openapi series — no auth, served to
anyone with the shop link. Everything it returns is visible to the world.
Apply that lens to every field.

## Target route — corrected during verification

    Target route: GET /v1/public/locations/{location_slug}/status
    Schema: LocationStatus (the same one API1 extended with next_open_at)

The spec as first written named `GET /v1/public/locations/{id}/info`. That
route does not exist — no path in openapi.yaml, no handler, no manual route,
nothing in openspec/. The landing page's actual endpoint is the status route
above, and that is where both fields belong: U1 needs mode and audiences on
first paint, the derivations fold into a query the handler already runs, and
API1 already put next_open_at there, so the landing page's whole data
contract lives in one place.

Note the parameter is location_slug, not location_id — every reference in
this spec is to be read accordingly.

The handler builds a hand-built map (API1 confirmed it at
handlers_public.go:795-805). Per the API1 ruling, existing routes are not
retrofitted — add the new keys to that map. Assign unconditionally so an
empty array marshals to [] rather than vanishing.

## Changes to LocationStatus

  available_modes: array of enum [walk_in, appointment]
    Which booking modes this location currently accepts, before any
    service is selected. Derived from the location's active
    service_variants: walk_in present if any active variant has
    allow_walk_in; appointment present if any has allow_appointment.
    An empty array is valid and means no bookable service is configured.

  audiences: array of enum [men, women, unisex]
    Distinct gender values across the location's ACTIVE
    service_categories. The client renders a chip row from this and
    hides it entirely when the array has one element — a men-only shop
    should not cost every customer a tap.

Both NOT in required.

## The appointment dark-out — verify and report before writing

`POST /v1/appointments/book` intentionally 401s for customers as a deliberate
Phase 1.5 gate.

If that is still true, `available_modes` returning `appointment` would
make the landing page render a "Book for later" CTA that leads to a dead
endpoint. Confirm the gate's current state and report it. Do NOT remove
the gate — that is a conscious product decision, not this unit's call.

Resolution if the gate is live: `available_modes` reflects the SCHEMA
(what variants allow), and the response carries a separate boolean
`appointments_enabled` reflecting whether the booking endpoint is actually
reachable. The client shows the CTA only when both agree. Document why
the two can disagree.

If verification finds the gate has been removed since, report that and
`appointments_enabled` is unnecessary.

## Verify before writing

1. The current shape of the public location response — every field it
   returns and how it is built. Report whether it uses a generated struct
   or a hand-built map (API1 found 96% are maps; this is an existing
   route, so it is likely a map, and per the API1 ruling existing routes
   are NOT retrofitted — new fields are added to the map).
2. Whether `service_categories.gender` values in practice cover all three
   enum values, and what a location with zero active categories returns.
3. Whether deriving available_modes requires a new query or can join onto
   an existing one in the handler's current path. Report the added cost —
   this is the most-hit public endpoint in the product.
4. The appointment dark-out's current state, per above.
5. Whether any index supports the derivation queries. `001` has
   `idx_service_variants_group` and `idx_service_categories_location`.
   A missing index is a finding for a later migration unit.

## Accept

- **A1** Spec edited, `make gen-api` against a clean-tree baseline,
  tool-only regeneration. Two (or three) new optional fields, no change
  to any existing field's type, name, tag or required status.
- **A2** A location whose variants all allow walk-in and none allow
  appointments returns `["walk_in"]`.
- **A3** A location with both returns both, order-stable.
- **A4** A location with zero active variants returns an empty array, not
  null, not an omitted key.
- **A5** `audiences` returns distinct genders across active categories
  only; an inactive category's gender does not appear.
- **A6** A single-audience shop returns exactly one element.
- **A7** `appointments_enabled` (if verification requires it) is false
  while the dark-out gate is in place, and the field is documented as
  reflecting endpoint reachability rather than schema capability.
- **A8** No existing key in the response changed — assert the full key set
  equals the POST-API1 set plus the new fields. next_open_at is now part
  of the baseline.
- **A9** No auth required; the endpoint still works with no JWT.
- **A10** Response time does not materially regress. Report the query
  count before and after.
- **A11** `make verify-api` exits 0.
- **A12** Full suite green.
- **A13** Decoded swaggerSpec carries the new fields with correct enums
  and required unchanged.

## Constraints

  generated struct.
- No migration.
- Do not remove or alter the appointment dark-out.
