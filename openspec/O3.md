UNIT: O3 — wait range fields on QueueEntryPublic

REPO: barberbase-core
BRANCH: from clean main after O2, clean working tree

CONTEXT
T3 shipped TierScopedWait returning (lo, hi). Only hi is serialised,
into the existing estimated_wait_minutes. lo is computed and tested
but never reaches the wire.

This unit adds both ends explicitly so a client can show a range
rather than a point estimate. estimated_wait_minutes stays and
continues to equal max — do NOT remove or repurpose it; it is a
required field and existing clients depend on it.

THE CHANGE
  QueueEntryPublic gains:
    est_wait_min_minutes:
      type: integer
      minimum: 0
      description: >
        Low end of the wait estimate, in minutes. Assumes every
        eligible barber becomes free immediately. Always <=
        est_wait_max_minutes; equal when at most one barber can
        serve this entry.
    est_wait_max_minutes:
      type: integer
      minimum: 0
      description: >
        High end of the wait estimate, in minutes. Equals
        estimated_wait_minutes. Prefer showing a range using both
        ends; if showing one number, show this one — under-promising
        on wait is the safe direction.

  Both NOT in required, for the same reason next_open_at was not:
  adding to required is a breaking change for any client that
  validates responses.

  Per the API1 ruling, do NOT put nullable or description beside a
  $ref anywhere. These are plain integers, so it does not arise —
  confirm it does not.

VERIFY BEFORE WRITING
  1. Where QueueEntryPublic is built. API1 found 96% of responses are
     hand-built map literals; O2 found QueueEntryPublic is one of the
     ~4% that is typed. Confirm which, because that determines
     whether the compiler enforces this or a hand edit is needed at
     every construction site.
  2. Every construction site of QueueEntryPublic, and whether each
     has access to lo. T3's report noted some paths hardcode
     PositionAhead: 0 (commands.go:697, handlers_public.go:420) and
     do not call TierScopedWait at all. Those sites cannot populate
     a real range. Report what each site currently does and what it
     can honestly provide.
  3. Whether estimated_wait_minutes is currently required in the
     spec. If it is, confirm max must equal it exactly and that no
     site can produce one without the other.
  4. Whether any site produces estimated_wait_minutes from something
     other than TierScopedWait — T3 listed handlers_push.go:250
     (count * 20) and intent_resolver.go as out of scope. If such a
     site populates QueueEntryPublic, it cannot honestly emit a
     range and must be reported.

  If verification finds sites that cannot produce a range, STOP and
  report before writing. The options are: omit the fields at those
  sites (they are optional), or make them nullable. Emitting a fake
  range is not an option — do not default lo to hi to fill the shape.
