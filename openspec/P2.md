# UNIT: P2 — public barber list

REPO: barberbase-core
BRANCH: from clean main after P1, clean working tree

## Context

The customer flow's barber screen (frontend unit U3) shows per-barber
price and live wait so a customer can trade money against time. That is
the highest-value screen in the flow and none of its data is public today.

P1's verification found `/status` already returns a public barbers array
(id, display_name, presence_state) under non-pooled routing, mapping
`staff_members.status` straight through. A customer can therefore already
see that a named barber is on break. That is a live privacy leak this unit
fixes, not one it introduces.

## Two parts

### Part A — fix the existing leak (do this first, it stands alone)

`staff_members.status` is an internal operational enum
(idle, cutting, break, offline). Map it to a public-safe value on every
public surface:

  internal        public
  idle       →    available
  cutting    →    busy
  break      →    busy
  offline    →    (omit the barber entirely)

A customer needs to know whether someone can cut their hair now. They do
not need to know that Amit is on a tea break, and the barber standing next
to a customer holding that screen does not need it broadcast either.

Apply to `/status`'s existing barbers array. This is a WIRE CHANGE to an
existing public field — report whether any client consumes
`presence_state` today (check barberbase-frontend) before changing it.

### Part B — the barber list for U3

New: `GET /v1/public/locations/{location_slug}/barbers`

Query param: `variant_ids` (repeated or comma-separated), optional. Price
and wait depend on the selection, so without it return the barber list
with availability but no price and no wait.

Per barber: `staff_member_id`, `display_name`, `tier` (id, name, rank),
`availability` (the mapped enum above), `est_wait_minutes`,
`price_paise`, `price_delta_paise`, `avatar_url`.

`price_delta_paise` is relative to the location's DEFAULT tier, not the
cheapest — anchoring to cheapest makes every barber an upsell. Negative
deltas are the point: a customer who came willing to pay the default price
and takes a junior for less, sooner, is revenue the shop was not
capturing.

## Fields that do not exist — report, do not invent

P1's verification confirmed `staff_members` has no `years_experience` and
no `specialities` columns. They are not in 001–004.

DROP both from this unit. Do not open a migration. A tier name and rank
already carry the signal a customer needs ("Senior · rank 30"), and
tenure claims are a schema change with its own unit.

## Ratings — explicitly excluded

There is no ratings table and this unit does not add one. In a four-chair
shop the barbers sit next to each other and can see the screen; a public
per-employee rating is a workplace problem before it is a product feature.
Do not add a rating, review count, or any public per-barber score.

## Verify before writing

1. Every existing public surface that exposes any `staff_members` field.
   `/status`'s barbers array is one — report whether there are others.
2. Whether `barberbase-frontend` consumes `presence_state` from
   `/status`. If it does, Part A breaks it and the frontend change is
   named in this unit's write list.
3. Whether `avatar_url` can be populated. M2 built the media pipeline and
   `media_assets` supports `purpose='staff_avatar'`, but media is disabled
   in prod. Report what the field returns when no avatar exists and when
   media is unconfigured — a monogram fallback is the frontend's job, so
   the API should return null, not a placeholder URL.
4. Whether `TierScopedWait` can be called per-barber, or whether it is
   entry-scoped and needs a variant. Report its signature. Per-barber wait
   for a customer who has not yet joined is a different computation from
   an existing entry's wait.
5. Whether the location's default tier is reliably resolvable — T1's
   `idx_staff_tiers_one_default` allows zero defaults. Report what
   `price_delta_paise` returns when no default tier exists.
6. Index coverage for the barber roster query with a tier join.

## Accept

- **A1** Part A: no public surface returns a raw `staff_members.status`.
  Assert the mapping on every surface found in verification item 1.
- **A2** An offline barber is absent from every public response.
- **A3** A barber on break shows as `busy`, indistinguishable from
  cutting. Assert a customer cannot tell them apart.
- **A4** Part B: the route is reachable with no auth.
- **A5** With `variant_ids`, each barber carries `price_paise` and a
  `price_delta_paise` relative to the default tier. Assert one negative
  delta and one positive.
- **A6** Without `variant_ids`, price and wait are omitted (not zero, not
  null) and the barber list still returns.
- **A7** `est_wait_minutes` is tier-scoped — a single-barber tier's wait
  is materially larger than a pooled barber's at the same queue depth.
- **A8** No default tier configured: `price_delta_paise` omitted, price
  still present. No panic, no divide-by-zero.
- **A9** `avatar_url` is null when no avatar exists and when media is
  unconfigured. Never a placeholder.
- **A10** No `years_experience`, no `specialities`, no rating field
  anywhere in the response. Assert by key-set.
- **A11** A tenant's barbers never appear on another tenant's endpoint.
- **A12** `make verify-api` exits 0.
- **A13** Full suite green.
- **A14** Decoded swaggerSpec carries the path with no security block,
  and the availability enum.
- **A15** Enum-constant reshuffle check: P1 found that adding an enum
  can silently rename constants on unrelated existing types. This unit
  adds an availability enum. Report any constant renamed outside the new
  types, and whether anything references it.

## Constraints

- Public endpoint. No staff phone numbers, no revenue, no internal
  status, no per-barber performance data of any kind.
- New route uses generated structs. `/status`'s existing map is not
  retrofitted — Part A changes a value in it, not its shape.
- No migration.
- Do not add columns that do not exist. Report and drop the field.
